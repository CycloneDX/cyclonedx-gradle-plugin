# Publish SBOMs and attest releases in the build platform

The plugin remains an SBOM producer: it does not generate or sign SLSA provenance. Its own releases publish the
implementation project's **Direct SBOM** as a versioned GitHub Release asset, while the hosted release platform
generates and verifies SLSA Build provenance for that **Published SBOM** and the main, sources, and Javadoc JARs. A
separate **SBOM Attestation** binds the implementation JAR to the **Published SBOM**. This keeps signing authority
outside user-controlled Gradle execution while making the SBOM independently available to consumers.

The release SBOM is intentionally generated by the latest already-published plugin version, rather than by the
candidate implementation being released. Advancing that bootstrap version happens after a release, so an unshipped
candidate does not produce its own release evidence.

The Gradle Plugin Portal accepts those three JAR forms but rejects JSON classifier artifacts. POMs, Gradle module
metadata, repository indexes, and checksum sidecars are generated or derived by the Portal rather than uploaded build
outputs, so they are outside the provenance subject set. The release platform, attestation storage, distribution
repository, and workflow mechanics may change without revisiting this decision as long as the trust boundary,
publication coverage, and artifact-to-SBOM boundary remain intact.
